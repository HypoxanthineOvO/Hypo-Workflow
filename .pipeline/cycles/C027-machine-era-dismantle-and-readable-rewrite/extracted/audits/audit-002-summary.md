# C21 前置扫描简报

> 详细证据见 [audit-002.md](./audit-002.md)。  
> 本轮只研究，不进入实现。

## 一句话判断

Hypo-Workflow 的问题不是功能少，而是功能、规则和平台投影已经很多，真实执行与效果验证没有同步跟上。现在适合先做一次架构收敛，不适合继续堆命令、规则或 adapter。

`BLOCKED` 只表示“先不要直接开始 vNext 实现”，不表示整个项目不可用。核心 helper 和单元测试依然稳定。

## 五个定性结论

### 1. RULES 的体感问题是真实的

RULES 已经有配置、优先级和提示词投影，但没有一套通用执行器去保证 `error` 真阻断、`warn` 真留下回执。它目前更像“规则说明系统”，还不是“规则门禁系统”。

### 2. Maintain 需要先修真实闭环，再讨论漂亮的新模型

现有 helper 很多，但真实全局 queue/ledger 已与当前 schema 不兼容；定时 Global Consolidation 没读到真实会话，仍每天生成通用空产物并被外围记成完成。原先“简化 Run、统一状态”的方向是对的，但第一步应是恢复数据权威和正确完成语义。

### 3. 平台能力假设已经落后

Codex、Cursor、Trae、Kimi Code 现在都有比仓库假设更丰富的 Plugin/Hook/Skill/Agent 能力。与此同时，本地 Claude/OpenCode Hook 的部分协议并没有真正对上宿主。下一版不能再按平台品牌复制一套大提示词，而应根据可验证能力生成最小适配。

### 4. 当前最大的工程债是“闭环”，不是代码量

Cursor 只有 41 个旧命令，而权威已经是 53 个；检查工具发现不了。配置默认值、架构文档、Hook runtime、plugin 版本也有多条基线。需要一张明确的 authority -> generated artifact -> runtime effect 图。

### 5. 现在还不知道哪些命令真的低频

日志没有命令调用和效果遥测，所以“没有命中文本”不等于“没有人用”。可以怀疑 53-command surface 太宽，但应先记录本地、脱敏的 invocation/outcome，再决定合并或弃用。

## 我建议暂时不要做的事

- 不要按“模型更强”直接删掉所有约束。可以先删行为脚手架，不能先删权限、外部副作用和状态不变量。
- 不要立刻增加 Kimi/ZCode adapter。先建立平台能力画像、原生格式和 smoke 标准。
- 不要直接把 Stash 做成 `git stash` 包装。更合理的产品概念可能是 Checkpoint/Suspend，Git 只是底层机制之一。
- 不要根据当前日志直接删除低命中命令。

## 下一轮最值得先聊什么

1. 哪些规则必须成为确定性硬门禁，哪些只是建议？
2. 能否接受“机械安全 / 工作流不变量 / 模型行为提示”三层约束模型？
3. Maintain 的核心到底是手动跨项目维护，还是定时自动化？二者是否分域？
4. 是否用一个版本化 Capability Profile 驱动 Claude、Codex、OpenCode、Cursor、Trae、Kimi、ZCode 的不同投影？
5. 是否接受默认本地、脱敏、不记录正文的命令与效果回执？
6. Checkpoint 首要解决的是任务切换、灾难恢复，还是并行实验？

## 当前验证状态

- 单元测试：687 / 687 通过。
- 系统回归：62 / 68 通过，6 个场景仍停在旧命令数、旧审计分类或旧文件名契约。
- 审计判定：6 Critical / 7 Warning / 3 Info。
- 本轮产品代码改动：0。

下一轮讨论建议从“哪些东西必须真的生效”开始，再谈命令精简和平台扩张。这样能够先把系统的骨架收紧，再决定哪些约束值得保留。
