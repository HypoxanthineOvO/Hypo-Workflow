# Plan

## 输出语言规则

用户可见内容跟随当前对话或项目语言；YAML key、命令、路径和必要专名保留英文。

Plan 是 Cycle 内包含一个或多个 **Stone** 的交付方式。Stone 是用户需要检查真实产物或作出决定的计划项；复杂度、文件数量和内部阶段数量本身不构成 Stone。Plan 部分（Discussion 与 Proposal）不进入 Milestone/Stone ID 空间，M/S ID 只编码 Proposal 批准后的执行部分。

## Discussion

Plan 默认是引导式规划讨论。除非用户明确要求直接从已给需求生成 Plan，否则必须先通过 Discover、Technical、Architecture 等范围相关主题讨论工作。

讨论从"澄清先行"开始，而不是直接给方案或最终回答：

1. 先搜索仓库与历史：读项目索引、当前 Cycle、相关 memory 与历史记录，弄清现状和已有决定，让分析建立在仓库事实上而不是通用模板上。
2. 在给出任何 Proposal 或最终回答之前，先完成三项分析并展示：
   - **假设**：指出用户没有明说、但已经默认成立的假设；
   - **缺口**：告诉用户还缺哪些关键信息，以及这些信息会如何改变方案；
   - **常见错误**：指出处理这类问题时最常犯的一个错误。
3. 然后提出最关键的一个或少数几个问题——目的是理解用户的真实目标和具体情况，让最终方案真正对用户有用，而不是谁都能套用的通用建议。信息已经充分时直接说明，不要为了问而问。
4. 等用户回答后再继续；未经讨论完成门不得直接写 Proposal。

写 Proposal 前必须：

1. 建立清晰、用户可见的讨论范围；
2. 逐项讨论该范围内的每一项；
3. 复盘范围项，明确询问用户是否都已充分讨论、是否可以开始写 Proposal。

只有用户在该检查点明确确认，才授权写 Proposal。"可以"、"对"、对某个想法或中间建议的认可只确认该内容，不关闭 Discussion、不授权写 Proposal、也不授权执行。Proposal 批准与执行授权是后面独立的 gate；绝不把讨论完成、写 Proposal、批准 Proposal、开始执行折叠成一次推断。

软件项目展示 Discover（用户需求、仓库事实、模型推断和未决用户决定）、Technical（现有与拟议技术、兼容性、依赖和验证工具）、Architecture（组件、边界、数据或控制流、改动点和下游影响）。这些内容可以一起展示，是讨论的素材，不是确认 gate。信息已经充分时直接说明，不为了轮数继续提问。

## 完整计划

1. 创建或聚焦一个 Cycle，并在 `PLAN.md` 写 `mode: plan`。
2. 不要把"规划/设计阶段"本身写成 M1（旧 Cycle 如 C12/C19/C22 曾犯此错）：讨论与 Proposal 属于 Plan 部分，不在 ID 空间内；M/S ID 只编码执行。
3. 使用稳定的人类可读 ID 编码全部 Milestone 与 Stone，例如 `M1 → S1 → M2`。开始后不重排或复用 ID。
4. 每行写清阶段、期望结果和验证方式。Stone 还要写清用户将看到的真实产物和接受标准。
5. `PROGRESS.md` 通过 `plan: PLAN.md` 指回计划，按相同顺序完整镜像全部 ID、状态、结果或证据和下一步。
6. `EXECUTION.md` 的每个 checkpoint 引用对应计划 ID。
7. 展示完整 Proposal，只询问一次是否确认并开始、确认但不开始或继续讨论。

普通 Milestone 验证后自动继续。Stone 完成时将该项标为 `waiting-review`，展示真实产物和核心报告内容，然后等待接受或拒绝。拒绝后解释失败原因和修正方案，将相关 Milestone 恢复为 `in_progress`，保留拒绝记录，不删除历史。

能力较强的主模型只读取薄 Plan。只有委派 Worker 时才生成详细 Handoff；不要把 Worker 操作手册塞进所有 Plan。
