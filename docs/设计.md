# Hypo-Workflow 3.0 设计

这份文档是 3.0 的设计依据，来自 2026-10-17～18 的讨论。旧版整体废弃，不迁移。

旧版本号与代际的对照：

| 代 | 旧 tag | 时间 | 思路 |
| --- | --- | --- | --- |
| 1.x | v6.1 – v12.8 | 2026-04 至 05 | 提示词与 Skill 驱动的 Plan/Milestone/Cycle 流水线 |
| 2.x | v13 – v15 | 2026-05 至 08 | Node runtime、manifest、hash、hooks 门禁；最后拆回人读文件 |
| 3.0 | v3.0.0 | 2026-10 起 | 只做一件事：边用边改时文档和代码一直对得上 |

## 1. 为什么重做

模型已经能自己做深度讨论、写计划、拆任务、用工具。旧版为弱模型设计的门禁、轮次、Cycle/Milestone、hash 校验、强制 Worker，现在大多变成负担：卡住正常工作，产生黑话，留下大量没人读的文件。旧版留在项目里的流程文件，停用之后仍会被 Agent 读到。

回看半年来和各家 Agent 协作的真实反馈，最痛的是：

1. 假完成：mock、测试通过、没重启就说做完。
2. 讨论和执行分不清：讨论中擅自开工；授权后又停下来要确认；被打回后不复盘就改。
3. 过度防御：hash、免责尾巴、“已核验”标注、硬编码测试。
4. 改了 A 坏了 B；只修被点名的一处。
5. 汇报只给路径和术语，没有结论。
6. 文档越堆越乱：规则只追加不替换，按日期堆文件，README 被过程信息污染，到处是 M1/C12 这类编号。

前三条靠几行行为规则解决；第四到第六条是新版要做的主要事情。

## 2. 定位

深度讨论别的工具都在做，再做没有额外价值。新版只做一件事：**在边用边改的过程中，让项目的文档和代码一直对得上。**

具体是：

- 项目现在是什么样，任何时候都能在一处读到，不需要推算哪条规则覆盖了哪条。
- 改一处时，能顺着记录找到会受影响的地方。
- 改完代码而没改文档，会被机械地查出来。
- 换一个 Agent 接手，读几个文件就能继续。
- 记录用人话写，不出现黑话、hash 和免责尾巴。

不做的：不做流程状态机，不做 Cycle/Milestone，不做 hooks 门禁，不强制子 Agent，不做 worktree（留给下一个大版本）。

## 3. 项目里的文件

```
项目/
  AGENTS.md          通用规则，所有项目同一份，由 Workflow 安装和升级，项目里不手改
  RULES.md           本项目的规则：文档地图、分工、汇报格式、禁区、构建与测试
  STATUS.md          项目进度：现在走到哪、下一步、卡在哪、以后
  BOARD.md           协作板：每个 Agent 此刻在做什么，互相留言
  README.md          只给项目的用户看
  <分区>/AGENTS.md   分区规则，按需增加
```

小项目可以只有 `AGENTS.md`、`RULES.md`、`STATUS.md`，其他的用到再建。

每个文件只有一类读者：

| 文件 | 给谁看 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| README.md | 项目的用户 | 是什么、怎么装、怎么用 | 开发过程、Agent 规则、进度 |
| AGENTS.md | 所有 Agent | 通用的干活方式 | 任何项目特有的内容 |
| RULES.md | 本项目的 Agent 和用户 | 东西放哪、谁负责什么、怎么汇报、怎么构建测试 | 产品现状、进度 |
| STATUS.md | 用户和 Agent | 项目整体进度、下一步、未决事项、以后 | 产品行为细节（链接到需求文件） |
| BOARD.md | 正在干活的 Agent | 各自当前在做什么、留言 | 已完成的事 |
| 分区 AGENTS.md | 写这个分区的 Agent | 这个分区怎么命名、写什么 | 别的分区的事 |

### 3.1 文档地图

`RULES.md` 里有一张表，列出项目里所有放记录的地方。写任何记录之前，先找到它在表里的位置，并读那里的 `AGENTS.md`。表里没有的地方不能新建记录；需要新分区要先问用户。

开发项目示例：

```markdown
## 文档地图
| 放什么 | 在哪 | 怎么写 |
| --- | --- | --- |
| 给用户看的说明 | README.md | 只写怎么打开、怎么用 |
| 产品现在的样子 | docs/需求/<功能>.md | 见 docs/需求/AGENTS.md |
| 用户认可的界面 | docs/截图/ | 验收参照，不是代码来源 |
| 部署与运维 | docs/运维/<主题>.md | 只写现在怎么部署和排障 |
| 过程材料 | docs/材料/ | 原样保存，不再更新 |
```

科研项目示例：

```markdown
## 文档地图
| 放什么 | 在哪 | 怎么写 |
| --- | --- | --- |
| 整体进度 | STATUS.md | 只写现在 |
| 用户定下的决定 | docs/决定.md | 按主题分组；推翻就改写并注明日期 |
| 一条研究线 | research/<线>/ | 见 research/AGENTS.md |
| 论文与文献 | papers/ | 见 papers/AGENTS.md |
| 原始数据 | data/ | 到货后不修改，见 data/AGENTS.md |
| 会议、转录、合作方原件 | sources/<来源>/<日期>-<名称>/ | 原样保存，不进 git |
```

目录层数不限制，随项目自然生长；只要求地图能链接过去。

分区规则示例（`research/AGENTS.md`）：

```markdown
# 研究线
- 每条线一个目录，README 开头三行：想回答什么、现在的结论、下一步。
- 实验放 experiments/日期-做什么/，README 写：问题、条件、结论。
- 结论被推翻：旧实验 README 顶部写"作废：原因，日期"，再改这条线的 README 和 STATUS.md。
- 重跑取代旧结果：旧目录归档，新目录沿用原名，不要 -v2、-final、编号。
```

分区规则每个不超过十来行，只写“东西放哪、叫什么、写什么”，不写流程步骤。

### 3.2 需求文件（产品现状）

开发项目里，产品现在的样子按功能分文件写在 `docs/需求/` 下（科研项目对应的是各研究线的 README）。每个文件只用以下小标题，没有内容的整节不写：

```markdown
# 同步

## 现在
逐操作同步；前台 5 秒、后台约 15 秒检查；冲突只挂起相关操作。

## 规则
- 不恢复成一个全局 localStorage 快照。

## 不能坏
- 正在输入的光标、草稿、滚动位置在刷新后保留。

## 牵连
事项状态、详情卡

## 代码
- plan_sync.py
- web/src/sync.js: mergeChanges, retryQueue

## 测试
tests/test_sync.py、tests/sync_browser.py

## 未定
- 离线超过一天的副本怎么合并。
```

- **现在**：行为描述，用户能看懂的话。
- **规则**：用户定下的决定。改主意就改写这一条，不追加“最新裁决”，不写日期段落。
- **不能坏**：用户确认过、任何改动都必须保持的行为。改动碰到这里要先告诉用户。
- **牵连**：会受这个功能影响的其他功能。只写这一边，反向关系由 `hw find` 算出来。
- **代码**：这个功能在哪些代码里，写到“文件: 函数”。
- **测试**：改这个功能要跑哪些测试。
- **未定**：还没想清楚、等用过之后再定的事。讨论时不必当场解决所有细节，放这里。

被推翻的内容直接删掉，历史在 git 里。

### 3.3 STATUS.md 和需求文件的分工

问一句：这条信息说的是“产品现在长什么样”，还是“项目现在走到哪”？

- 前者只写在需求文件（或研究线 README）里。
- 后者写在 `STATUS.md`：哪些已上线、下一步做什么、卡在哪、等用户决定什么、以后要做什么。

`STATUS.md` 不复述产品行为，最多链接过去。这样“现状”只有一个来源。

`STATUS.md` 里的“以后”一节记录明确的未来需求，每条写清做什么、参照什么、什么时候开始。开始做时从这里删掉，搬进 BOARD。

### 3.4 BOARD.md（协作板与交接）

不写交接文档。BOARD 随工作实时更新，换 Agent 时直接读它。

```markdown
# Board

## 各 Agent 当前
### Codex GPT · 后端
- 更新：2026-10-18 21:40
- 在做：同步冲突修复
- 做到哪：服务端按字段合并完成；前端重试写了一半
- 下一步：补 web/src/sync.js 重试，跑 test_sync.py
- 未提交：web/src/sync.js、plan_sync.py

## 留言
- [10-18 21:40 Codex GPT → Claude Opus] 同步规则改了，请更新 docs/需求/同步.md
- [10-18 20:15 Claude Opus → 用户] "本次不去是否计入完成率"没定，等你决定
```

- 每个 Agent 只改自己那一道，覆盖写，带更新时间。在自然节点更新（完成一小步、准备停下），额度突然用完也最多丢最后一小段。
- 留言只追加；处理完就删掉，结果写进它该去的文档。等用户决定的留言一直保留，直到用户决定。
- 没有“已完成”列表。做完的结果进需求文件或 STATUS，过程进 git。
- 开工前先看 BOARD：如果另一个 Agent 那一道列着你要改的文件，先告诉用户，不要直接改。

### 3.5 分工

`RULES.md` 里的分工表由用户填，模板不推荐任何模型（模型换代太快）：

```markdown
## 分工
| 谁 | 负责什么 | 不碰什么 |
| --- | --- | --- |
| （例如 Claude Opus） | （例如 文档、需求整理） | （例如 后端代码） |

子 Agent：（用哪个模型做阅读和批量修改；不填就由主 Agent 自己决定）
```

通用规则里只写分工的方式：大量阅读、搜集、批量机械修改交给子 Agent；派活写清做什么、怎样算做完、不许碰什么、结果要带可核对的证据；子 Agent 的结论抽查后再用；小事自己做。

### 3.6 汇报格式

不预置模板。项目里说“讨论一下汇报格式”，Agent 根据项目性质出草稿，用户确认后写进 `RULES.md`。开发项目可能是“结论、改了什么、怎么亲手看到、风险”；写小说可能是“这章写了什么、和大纲的偏差、待你决定的情节”。

没定格式时的兜底：先说结论；内容在对话里讲清楚，不只给文件路径。

## 4. 提交格式

Agent 每完成一小步自己提交。提交信息格式固定，不按项目改：

```
同步：冲突时只重试相关操作

前端重试队列改为按 opId 单独重试，失败的操作不再拖住整页保存。
原因：多设备同时编辑时整页报冲突。

Feature: 同步
Code: web/src/sync.js: retryQueue, mergeChanges
Docs: docs/需求/同步.md
Verified: tests/sync_browser.py 通过；两台设备同时改同一事项，只挂起冲突项
```

- 第一行：功能名加一句人话总结。不写 `feat:`、编号、hash。
- 正文：做了什么、为什么，用户能看懂的话。
- 末尾字段（git trailer，`hw` 靠它们解析）。git 只认 ASCII 字段名，所以字段名用英文，值写中文：
  - `Feature`：动了哪几个功能，对应需求文件名（科研对应研究线）。
  - `Code`：精确到“文件: 函数”。
  - `Docs`：改了哪些文档；没改写原因，例如“未改，纯重构，行为不变”。
  - `Verified`：在哪里亲眼看到了结果。

这样过程历史按功能可查，不需要另写流水文件。

## 5. 通用 AGENTS.md 里的行为规则

```markdown
## 怎么干活
- 我在描述想法、提问、抱怨时，是在讨论：先说你的理解和方案，不改文件。
- 我说开始之后，一口气做完。只在三种情况停下：要动"不能坏"的东西、不可逆或对外的操作、超出说好的范围。
- "做完"指在我真实使用的入口上看到结果，不是测试通过或文件写好。
- mock 是验收参照，不是代码来源；正式实现不复制 mock 的代码和标记。
- 说做完之前跑 hw check，并按它的提示更新文档。
- 汇报在对话里讲清楚，格式以 RULES.md 为准。
- 不写免责尾巴和自证标注；不确定的事直接问我，不要写进文档。
- 命名必须自带含义：日期、作者、做什么都可以；不用要查表才懂的代号、编号和 hash。
```

（完整内容见仓库根目录的模板，写在实现阶段。）

## 6. 两种工作节奏

项目前期，用户会像这次一样细致讨论；中后期往往只说一句“维护一下”“升级一下”。两种节奏都要接得住：

- **前期细讨论**：讨论的结论最终落在文档地图、需求文件的“现在/规则/不能坏/未定”和 STATUS 里。不要求一次想清所有细节，没定的放“未定”。
- **后期一句话**：Agent 从 STATUS（下一步、未决、以后）、BOARD（留言）、需求文件（未定）和 `hw check` 的报告里找事做，先说出它打算做哪几件、为什么，再开始。

这一节还没想透，试用阶段重点观察。

## 7. hw：给 Agent 用的查询和检查工具

一个小 CLI，只读、只报告，不改文件。用户不直接使用，Agent 按 `AGENTS.md` 的约定调用。用 Python 3.10+ 标准库实现，没有第三方依赖；`uv tool install` 装成全局命令，没装的机器也能直接 `python3 -m hw` 运行。选 Python 而不是 Node：用户能读能改，四台机器都有，sqlite/jsonl/git 解析标准库就够，旧版的 Node 分发复杂度不再出现。

| 命令 | 做什么 |
| --- | --- |
| `hw map` | 列出文档地图：每个分区、规则摘要、文件数 |
| `hw find <词>` | 按地图找相关的需求条目，显示现在、牵连（含反向）、代码、测试，以及 BOARD 里谁在动相关文件 |
| `hw status` | STATUS 和 BOARD 摘要；等用户决定的事项；BOARD 列的未提交文件与 `git status` 是否一致 |
| `hw log <功能>` | 按提交字段列出动过这个功能的提交：第一行和验证 |
| `hw check` | 检查，见下 |
| `hw handoff` | 找这个目录最近的会话（Codex、Claude、VSPi、Kimi Code、OpenCode、ZCode、DSH），抽出用户的话和最后几轮汇报；解析不了就返回会话文件路径，让 Agent 直接读 |

### 7.1 hw check 查什么

按重要程度：

1. **改了代码没改文档**（最核心）：
   - 提交声明了 `Feature: X`，但 X 的需求文件没变，`Docs` 字段也没写原因。
   - 提交改动的函数被某个需求条目的“代码”锚定，而这个功能没出现在 `Feature` 字段里（可能漏了牵连）。
   - 改动的代码文件没有任何需求条目描述（提示补条目，或在 RULES.md 标为不需要描述）。
   - 需求条目里的锚点找不到对应文件或函数。
2. **提交格式**：缺字段、第一行有编号或 hash。
3. **黑词**：按内置的规则表（`hw/blacklist.py`），分“报警”和“提示”两级；扫文档和最近的提交信息。
4. **地图**：地图外的记录文件、地图里不存在的分区、失效链接。
5. **README**：混进进度、Agent 规则、日期段落。
6. **BOARD**：留言没清（收件 Agent 更新时间晚于留言）、某一道超过 7 天没更新、出现已完成列表、总长度超过约 80 行。
7. **敏感文件**：`.env`、key、token 这类被 git 跟踪。

“改了代码没改文档”只能查出该改没改，查不出改得对不对；后者靠汇报和用户看。

## 8. 接入项目（init）

接入项目的时候用户要主动说一句。项目装好之后不再需要斜杠命令，用户说自然语言，Agent 读 `AGENTS.md` 知道对应做什么（“继续”就读 BOARD；“检查一下文档”就跑 `hw check`；“讨论一下分工”就出草稿写进 RULES.md）。

init 做的事：

1. 扫描项目：类型、目录、现有文档、代码结构。
2. 旧记录整块归档，不读不改不转写：旧 `.pipeline`、按日期堆的报告移进归档目录（加进 gitignore，或移到别的机器），地图里写明“旧记录，可能不是事实，不得引用”。
3. 现有 `AGENTS.md`、`CLAUDE.md` 里的项目规则整理进 `RULES.md`，根目录换成通用 `AGENTS.md`。
4. 按研究、开发、写作三种起步模板，给出文档地图和分区规则初稿，和用户讨论后写入。
5. 从代码和用户的话（不从旧文档）建立需求文件初稿：按功能切分，填“现在、代码、测试”，其余和用户逐步补。
6. 分工表留空，问用户怎么分。

希望 init 能由便宜的子 Agent（例如 DeepSeek Flash）完成大部分工作，这样可以批量规范现有项目。需要专门测试它能不能做到，见第 11 节。

### 8.1 用户叫才做的操作

有几件事很常用，但不是每次都该做。写进 AGENTS.md 就会变成固定要求，在极简的改动里只是拖慢，所以做成和 init 并列的 skill：有名字，用户说一句就做，AGENTS.md 里不提，Agent 也不主动跑。

| skill | 用户怎么说 | 做什么 |
| --- | --- | --- |
| `hypo-workflow-experience` | “用 Hypo-Workflow 体验一下” | 派一个没看过代码的子 Agent，只拿 README 和用户入口，按 RULES.md 写的用户身份走一两个真实任务，汇报卡在哪、README 哪里对不上；不改文件 |
| `hypo-workflow-cleanup` | “用 Hypo-Workflow 清理一下” | 按 RULES.md 和需求文件的“不能坏”，清掉没用的代码、重复写法、和代码对不上的文档、过时的规则；先列清单，确认后动手 |

体验针对的是半年来最常见的问题：Agent 不站在用户那边，README 乱写，测试只测内部现象。写代码的 Agent 知道实现，会不自觉替用户补上缺的步骤，所以要换一个只拿到用户材料的人去走。它查的是“README 和真实行为对不对得上”，这一层 `hw check` 查不到。

清理的标准来自项目自己的文档，不来自 Agent 的口味；没有标准的清理会把能用的东西改坏。

## 9. 宿主

- 其他宿主（Codex、Claude Code、OpenCode 等）只靠根目录 `AGENTS.md` 引导。不做 hooks。
- 只明确适配 VSPi：唤醒时读 BOARD 里写给自己的留言；派子 Agent 时读 RULES.md 分工表里用户填的模型。VSPi 那边的改动在 VSPi 仓库单独做。

## 10. 黑词库

规则表在 `hw/blacklist.py`，分报警和提示两级。来源是真实协作中反复被要求删掉的词句，以及能核实来源的公开 AI 用语词表。

- 免责尾巴（“不能声称……”“不代表……”“这验证……不替代……”）和自证标注（“已核验/未核验”）报警。
- 内部编号要结合语境：只有同时出现“Milestone/Cycle/阶段”才对 `M\d+`、`C\d+` 报警。
- “不是……而是……”这类句式只提示，不做门禁。

## 11. 怎么判断新版有没有用

先在一个开发项目和一个科研项目上各试用两周，看：

1. **文档跟没跟上**：`hw check` 报出“改代码没改文档”的次数，以及 Agent 是否当场修掉。
2. **牵连漏没漏**：有没有“改 A 坏 B”，而 B 本来就在 A 的牵连里。
3. **用户还骂不骂**：假完成、擅自开工、授权后还停、过度防御这几类，对比试用前后两周的会话记录。

另外单独测 init：让便宜的模型对现有项目跑 init，看文档地图、需求切分、旧记录归档是否合格，以及会不会写进黑词和编号。合格的话，就能用它批量接入现有项目。

两周后，没起作用的规则删掉；反复出问题的地方再补规则，并写明是因为哪次事故加的。判断一条规则留不留，问：删掉它，Agent 会因此犯错吗？不会就删。
